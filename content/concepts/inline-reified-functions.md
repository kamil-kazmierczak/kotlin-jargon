## Overview

An `inline` declaration asks the compiler to substitute supported function code and inlineable lambda bodies at call sites. That source-level choice enables non-local returns and reified type parameters in specific contexts, while also changing generated bytecode size and API constraints. It is not automatically faster.

## Why it matters to Java developers

Java developers may associate inlining only with a later JIT optimization. Kotlin `inline` is a source and compiler feature with observable language effects before the JVM JIT runs. It can remove some function-object and call overhead, but generated call-site bytecode may grow, public inline bodies constrain binary evolution, and actual performance still requires measurement.

## Mental model

Separate four questions. Source semantics decide whether a lambda may return from its enclosing function. Compiler generation may copy bodies and specialize access to a reified type. JVM execution and the JIT make further runtime decisions. API design determines which implementation details become embedded in callers.

## Semantics

An unqualified `return` inside a lambda passed directly to an eligible inline function can return from the enclosing named function; this is a non-local return. `crossinline` forbids that when the inline function may invoke the lambda from another execution context. `noinline` keeps a lambda as a value that can be stored or passed where inlining is not allowed. A `reified` type parameter is permitted only on an inline declaration and makes supported type checks, casts, and class literals available without an explicit `Class` or `KClass` argument. Type erasure still applies inside erased nested generic arguments, so reification does not make every runtime type test possible.

## Example

```kotlin run id=functions-inline-control-flow file=InlineControlFlow.kt main=InlineControlFlowKt expected=3:none
fun firstRejected(values: List<Int>, accepted: (Int) -> Boolean): String {
    values.forEach { value ->
        if (!accepted(value)) return value.toString()
    }
    return "none"
}

fun main() {
    println("${firstRejected(listOf(2, 3, 4)) { it % 2 == 0 }}:${firstRejected(listOf(2, 4)) { it % 2 == 0 }}")
    // 3:none
}
```

Standard-library `forEach` is inline, so the unqualified return exits `firstRejected`, not merely the lambda. A labeled `return@forEach` would be local to that lambda invocation. A plain non-inline higher-order parameter cannot grant this non-local control flow.

```kotlin run id=functions-reified-access file=ReifiedAccess.kt main=ReifiedAccessKt expected=String:Ada|Kotlin
inline fun <reified T> Iterable<*>.valuesOfType(): List<T> =
    filterIsInstance<T>()

fun main() {
    val values: List<Any> = listOf(1, "Ada", 2L, "Kotlin")
    val names = values.valuesOfType<String>()
    println("${String::class.java.simpleName}:${names.joinToString("|")}")
    // String:Ada|Kotlin
}
```

The compiler can emit the relevant runtime `String` checks at this call site. A non-inline alternative would accept an explicit class token or predicate; reified syntax is convenience backed by call-site generation, not erased-generic magic.

```kotlin run id=functions-readable-api file=ReadableFunctionApi.kt main=ReadableFunctionApiKt expected=refund:75
data class Event(val kind: String, val payload: Any)
data class Payment(val cents: Int, val refunded: Boolean)

fun String.normalizedKind(): String = trim().lowercase()

inline fun <reified T : Any> Iterable<Event>.firstPayloadWhere(
    kind: String,
    predicate: T.() -> Boolean
): T? {
    val expectedKind = kind.normalizedKind()
    return firstNotNullOfOrNull { event ->
        val payload = event.payload as? T
        payload?.takeIf { event.kind.normalizedKind() == expectedKind && predicate(it) }
    }
}

fun main() {
    val events = listOf(
        Event(" charge ", Payment(100, false)),
        Event("refund", "legacy"),
        Event(" REFUND ", Payment(75, true))
    )
    val refund = events.firstPayloadWhere<Payment>("refund") { refunded }
    println("refund:${refund?.cents}")
    // refund:75
}
```

The API gives the collection operation a precise name, keeps normalization in a focused extension, makes the payload type explicit at the call site, and uses a receiver predicate only where `Payment` members are the clear focus. Its single traversal, first-match order, null result, and predicate invocation policy are part of the contract. Reified access improves this Kotlin call but creates an inline-only API that needs a separate design if Java callers require it.

## Java comparison

Java commonly passes `Class<T>` to a static generic helper and uses an ordinary functional interface for the predicate. That form is explicit and callable from either language. A Kotlin reified function has no normal Java call that supplies a reified type argument, so libraries often expose a class-token core or Java-friendly overload and layer the reified Kotlin convenience on top.

## Common mistakes

Adding `inline` as a universal performance annotation, overlooking bytecode growth at many call sites, allowing an accidental non-local return to escape a large function, assuming reification preserves nested generic arguments such as `List<String>` completely, exposing a reified-only public API to Java, or packing several implicit receivers into a clever but unreadable DSL.

## Decision guidance

Use inline when its language capabilities or measured call overhead justify the generated-code and compatibility costs. Use `reified` for a Kotlin-facing convenience that truly needs the runtime type and provide a class-token or non-inline core when Java access or code-size control matters. Use `crossinline` and `noinline` from the lambda's actual invocation and storage requirements. Prefer explicit loops, parameters, or named policy types when inline receiver tricks obscure control flow.

## Knowledge check

Does `inline` promise that a function allocates nothing or runs faster? No. It directs compiler transformation and enables language features; captures, remaining `noinline` lambdas, call-site growth, JVM optimization, and workload determine runtime effects. Can reified `T` reliably prove that a value is `List<String>` rather than `List<Int>`? No; nested generic arguments remain erased in the usual runtime representation.

## Interview question

Design a Kotlin and Java-facing event query API that filters by payload type and accepts a predicate. Decide where to use inline, reified types, a class token, receiver syntax, `crossinline`, or `noinline`, then defend readability, binary evolution, and performance claims.

## Essential points

- Inline source semantics, emitted bytecode, runtime performance, and public API constraints are separate claims.
- Eligible inline lambdas permit non-local returns; `crossinline` and `noinline` encode real invocation constraints.
- Reified parameters enable supported runtime type operations but do not defeat all type erasure.

## Trade-offs

Inlining can remove some call and function-object machinery and unlock expressive APIs. It can duplicate bytecode, couple compiled callers to a public inline body, and make control flow less local. Reified convenience avoids explicit type tokens for Kotlin callers, while a token-based core remains easier to call from Java and can centralize implementation.

## Common traps

Promising speed from syntax alone, confusing Kotlin compiler inlining with JVM JIT inlining, changing a public inline body without considering already compiled callers, or using non-local returns where a named result would communicate intent better.

## Follow-up probes

When is `crossinline` required? Which lambda must be `noinline` if it is stored? How would you expose the API to Java, measure it, and test behavior after separate compilation?
