## Overview

Kotlin declaration-site variance helps Kotlin callers, while Java sees use-site wildcards in generated generic signatures. The mapping depends on position, so a cross-language API needs a real Java caller test.

## Why it matters to Java developers

A Java client may accept `Producer<Derived>` where a method expects `Producer<? extends Base>`, but not where it expects invariant `Producer<Base>`. A Kotlin annotation that changes this signature can break Java source compatibility even when Kotlin source still compiles.

## Mental model

Read the Kotlin generic declaration, predict the Java signature at each method boundary, then compile representative Java calls. Keep runtime erasure separate from source-level generic compatibility.

## Semantics

For a covariant Kotlin `Producer<out T>`, a parameter position commonly becomes `Producer<? extends Base>` in Java, while a return position commonly omits the wildcard. `in` maps to a lower-bounded Java wildcard in corresponding parameter positions. The compiler can omit useless wildcards for final types. `@JvmWildcard` requests one where it is not generated by default; `@JvmSuppressWildcards` suppresses one. These annotations change the Java-facing generic signature, not Kotlin's variance rules or JVM erasure.

## Example

The Java call relies on the generated wildcard for the Kotlin method parameter. A suppressed wildcard on `strict` would reject the same `Producer<Child>` input.

```kotlin run id=interop-wildcard-client file=GenericApi.kt main=GenericClient expected=child
open class Parent(val label: String)
class Child : Parent("child")
class Producer<out T>(val value: T)

object GenericApi {
    @JvmStatic fun read(source: Producer<Parent>): String = source.value.label
    @JvmStatic fun strict(source: Producer<@JvmSuppressWildcards Parent>): String = source.value.label
}
```

```java run id=interop-wildcard-client file=GenericClient.java main=GenericClient expected=child
public final class GenericClient {
    public static void main(String[] args) {
        Producer<Child> child = new Producer<>(new Child());
        System.out.println(GenericApi.read(child)); // child
        // GenericApi.strict(child) would fail Java generic type checking.
    }
}
```

## Java comparison

Java expresses variance at each use with `? extends` or `? super`; Kotlin often declares variance on the type parameter. Neither language can generally inspect `T` at runtime after erasure.

## Common mistakes

Assuming Kotlin `out` means Java always gets a wildcard; suppressing one to make a reflection signature look simpler without testing callers; or confusing an erased JVM descriptor with its generic signature metadata.

## Decision guidance

Use generated wildcards when they support intended Java substitution. Add `@JvmWildcard` or `@JvmSuppressWildcards` only after inspecting the emitted signature and compiling intended Java clients. Keep bytecode signature and source compatibility tests for published APIs.

## Knowledge check

Why might `Producer<Child>` work for `read(Producer<Parent>)` from Java? The generated parameter is commonly `Producer<? extends Parent>`, so it accepts a producer of a subtype.

## Interview question

A Java consumer stops compiling after a Kotlin API adds `@JvmSuppressWildcards`. Explain the likely before/after signatures, identify what to inspect, and propose a compatible design.

## Essential points

- Kotlin declaration-site variance may generate Java use-site wildcards.
- Position and finality affect wildcard generation.
- JVM annotations can alter Java source compatibility without changing Kotlin variance.

## Trade-offs

Wildcards increase Java assignability but can complicate method signatures. Suppression simplifies a declaration for some tools while potentially rejecting valid Java subtype producers.

## Common traps

Claiming wildcard signatures preserve generic arguments at runtime, or applying suppression globally before observing a real client problem.
